# MCP 开关的持久化边界：设计方案

> 状态：方案 B 已实施（0.7.0）；方案 A 已实施（0.8.0）
> 关联：GitHub `Max-Null/dsh-skill-mcp-center#6`、`#7`、`#8`；`docs/设计/Skill与MCP管理中心-spike记录.md` §1.5

## 一、问题

面板关掉一个 MCP server，重启 DSH 后它又回来了，工具重新注入会话（#6 实测：一个 `rea` server 207 个工具）。

根因不在插件，在宿主：

- `ctx.loader.update(id, { disabled })` 在**内存树**上生效——`Entry.update` 会 `_dispose` 掉 fiber，连接断开、工具卸载，当次运行立即见效。
- 但 `EntryTree.update` 结尾调用的 `source.tree.write()` 落到 `Loader.write()`，而它是空函数：`@deepseek-ai/cordis-plugin-loader@1.0.2` 的 `lib/index.js:715` 是 `write() {}`，DSH 源码 `vendor/loader/src/index.ts:171-173` 的注释写明「Loader's root tree is in-memory; writes are no-ops」。
- 重启后从 `cordis.yml` / `cordis.patch.yml` 重新加载，`disabled` 不存在 → 恢复启用。

一句话：**开关的效力只到本次运行，但界面按「持久设置」的语义呈现它。**

代价是可量化的（#8 作者实测，DSH 0.2.2-rc.1 / contextWindow 1,048,576）：挂着 `rea` 这个 server 时工具面 285 个、`tools` 序列化 322,811 字符（约 80,707 token）；关掉后 53 个、48,539 字符（约 12,139 token）。**每个会话的纯前缀开销差 68,568 token（−84.9%）**。这是方案 A 的动机。

## 二、目标与非目标

**目标**：面板上有一个动作，能让某个 MCP server 的「关」**活过重启**——不需要用户手写 YAML。

**非目标**：
- 不向上游发 feature request（方案 C，独立动作，不在本库交付里）。
- 不改 `mcpStatus()` 的状态推导——`entry.disabled` 本身是对的（读 `options.disabled` 与祖先链）。
- 不改 MCP 的增删改是否落盘（`createMcpServer` / `updateMcpServer` / `removeMcpServer` 只动内存树），见 §七。

## 三、事实基础

方案 A 的正确形态由下面五条事实决定，每条都有代码位置或实测。

### 3.1 层叠顺序，later wins

`packages/boot/app-boot/src/profile-context.ts:63-70` 的 `readProfilePatches` 按顺序拼一个扁平列表：

```
1. 各 bundle 的 cordis.patch.yml（按 dsh.profile.bundles 顺序）
2. 当前 profile 的 cordis.patch.yml
3. $DSH_HOME/cordis.patch.yml（home 层）
4. 启动层 --patch 等 overlays
```

这个列表整体交给根 Include，`applyEntryPatches` **一次性**按顺序应用。所以后面层里的 `- id: <x>` 能覆盖前面层（含 `insert`）产生的条目，且 home 层是**可写层里优先级最高的**。

### 3.2 只有当前 profile 会被加载

同上，第 2 项只读 `context.patchPath`，即**当前 profile**。`$DSH_HOME/profiles/` 下的其他 profile 文件对运行时**完全不存在**。

多 profile 共存是常态而非边角：本机 `~/.dsh` 有 `desktop`（5 条）与 `ssid`（31 条）两个 profile，**4 个 id 重合**（`agent-default-model`、`ui-chat`、`ui-settings`、`ui-settings-account`）。

推论：遍历 `profiles/*` 找可写目标，会写出「不生效但报成功」，并把别的 profile 的状态显示到当前面板上。

### 3.3 顶层覆盖不触碰既有条目

真实 patch 里的 MCP 条目长这样（`~/.dsh/profiles/ssid/cordis.patch.yml`）：

```yaml
- insert:
    - id: mcp-playwright-headless
      name: '@deepseek-ai/dsh-mcp-client'
      # CLI 缺失时停用：…会让整棵插件树加载失败、内核起不来。
      disabled: !!js '!process.env.SSID_MCP_PW_CLI'
      config:
        serverName: playwright-headless
```

`disabled:` 的值是 `!!js` 条件表达式，且带注释解释了它是一次安全开关。**就地改写这个字段会毁掉那次求值的语义；删掉整行会让条目永远启用**——CLI 缺失时就是内核起不来。

顶层覆盖不动它。实测（`applyEntryPatches`，空 base）：

| 输入 patches | 结果 |
|---|---|
| `[{insert:[{id:y, disabled:false, config:{b:2}}]}]` | `disabled:false`，`config` 在 |
| `+ {id:y, disabled:true}` | **`disabled:true`，`config` 在** |
| 去掉那条覆盖 | **`disabled:false` 完全还原** |

所以「持久禁用 = 追加一条顶层覆盖，解除 = 删掉它」是**可逆且不侵入**的。`insert` 子条目里的 `!!js`、注释、字段顺序一字不动。

### 3.4 profile-seed 会退役模板拥有的顶层块

`apps/desktop/src/ssid/profile-seed.ts:485-486`：

```ts
if (block.entries.length === 0) {
  // 顶层 `- id: x` 块：整块即一条，命中即退役。
  if (!block.ids.some(id => owned.has(id))) keptBodies.push(block.body)
  continue
}
```

`owned` 来自 SSiD 包内模板 `resources/ssid-plugins/cordis.patch.yml`，实际内容是：

```
mcp-playwright-headless, mcp-playwright-headed, mcp-codegraph,
connection, session-persistence-jsonl, plugin-market
```

**工具最多的三个 MCP 条目（playwright ×2、codegraph）都在 `owned` 里。** 写进 profile 层的顶层覆盖，会被下一次 seed 整块退役——正好是省 token 收益最大的那三个。而 `mcp-github` / `mcp-zhihu` 这类用户自加的条目不在 `owned` 里，profile 层对它们安全。

这个差异依赖一份插件拿不到的跨包内部知识。**不区分，统一写 home 层**——`$DSH_HOME/cordis.patch.yml` 不在 seed 的地盘上，优先级又最高。

### 3.5 面板新建的条目不在任何文件里

`createMcpServer` 走 `loader.create`（`src/service.ts:546-552`），只活在内存。它不会出现在任何 `cordis.patch.yml` 里，所以覆盖它对它无效（实测：`applyEntryPatches` 对不存在的 id 只 warn `patch: entry not found`）。重启后它本身就消失了。

## 四、方案 B：把边界写进界面（已实施，0.7.0）

保持现状，它是方案 A 的诚实下限——即使做了 A，条件表达式、内置 patch 这些情形仍然只有 B 说得清。

| 位置 | 文案 | 解决什么 |
|---|---|---|
| MCP 区块标题下 | 「开关只对本次运行生效，重启后恢复」 | 一次讲清规则 |
| 开关为「关」且本次运行被面板改过 | 「本次运行已停用 · 重启恢复」 | 关掉的当下看得见后果 |

判据是 `disabled && sessionToggled`，不是裸 `disabled`：手写 patch 或用 `!!js` 条件停用的条目不该被说成「重启恢复」。

## 五、方案 A：把「关」写进 home 层

### 5.1 写哪里

**唯一写入目标**：`$DSH_HOME/cordis.patch.yml`（`DSH_HOME` 缺失时取 `~/.dsh`）。理由是 §3.1（优先级最高）、§3.4（不受 seed 影响）、§3.5（不依赖条目来源）。

**读取目标**：home 层 + 当前 profile 的 patch（`ctx.profileContext?.patchPath`）。读 profile 是为了认出手写的 `disabled: true` 也能如实标注为持久；读**不**遍历其他 profile。

`ctx.profileContext` 由 `apps/cli/src/profile-boot.ts:287-295` 在 boot 之前 provide，含 `name` / `dir` / `patchPath` / `home`；类型来自 `@deepseek-ai/dsh-app-boot`，需要进 `peerDependencies`（`devDependencies` 同步）。它只在 dsh 启动的 profile 里存在，缺失时读取退化为只有 home 层——写入不受影响。

**代价要写在界面和 README 里**：home 层对所有 profile 生效。同一台机器上跑两个前端时，在一个前端里「永久禁用」会让另一个也看不到这个 server 的工具。

### 5.2 怎么表达

写入**只做顶层覆盖**，格式与 `plugin-manager` 的 toggle 一致：

```yaml
- id: mcp-playwright-headless
  disabled: true
```

**永不修改 `insert` 子条目内的任何字段**（§3.3）。这条是硬约束，不是风格偏好。

### 5.3 定位

- **id 归一**：运行时 id 可能是 `include:<x>`（根 Include 的 id 是 `include`，见 `app-boot/src/index.ts:575`；`EntryTree.sep` 是 `:`），文件里存裸 id。逐层剥前缀：`include:a:b` → `a:b` → `b`，精确匹配优先。
- **只认顶格块**：`^(\s*)-\s*id:\s*['"]?<bare>['"]?\s*(#.*)?$`，要求 `\s*` 为空或纯缩进且块层级为顶层。行尾注释必须容忍（`- id: x # 说明` 是自然写法）。
- **字面量才可信**：`disabled:` 的值为字面 `true` / `false` 才判定；`!!js ...` 视为不可判定，**不计入** `permanentDisabled`。运行时是否真的禁用由 `entry.disabled` 说。
- **重复取最后**：同文件内同 id 可出现多次，`applyEntryPatches` 的 `entryMap` 是后者覆盖前者，所以**最后一个**才是生效的那个。`~/.dsh/profiles/ssid/cordis.patch.yml` 里 `plugin-market` 出现 12 次，重复是常态。

### 5.4 写盘

- **禁用**：home 层已有该 id 的顶格块 → 确保块内 `disabled: true`（已是则幂等，不是则就地改这一行）；没有 → 文件末尾追加两行。追加位置在文件末尾等于该文件内优先级最高。
- **解除**：删掉顶格块里的 `disabled:` 行；若该块除 `- id:` 外已无其他字段，连块一起删（这是我们自己追加的形态，留下孤立 `- id:` 没有意义）。
- **保真**：按行编辑、不重新序列化；保留 CRLF（按原文件的 EOL）；写入走临时文件 + `rename`，失败时清理临时文件。
- **热生效**：写盘后同一次调用里 `ctx.loader.update(id, { disabled: disabled ? true : null })`，并清掉该 id 的 `sessionToggled` 记账（它不再是「本次运行改过」）。
- **幂等**：目标状态已成立时 `changed: false`，不写盘、不改文件 mtime。

### 5.5 状态与界面

三种「关」必须可区分：

| `permanentDisabled` | `disabled` | 卡片 |
|---|---|---|
| false | false | 正常启用 |
| false | true（`sessionToggled`） | 「本次运行已停用 · 重启恢复」 |
| true | true | 「已在 cordis.patch.yml 持久禁用」+ 「解除持久禁用」按钮 |

第四种组合（`permanentDisabled && !disabled`）**不允许出现**：`permanentDisabled === true` 时普通开关置灰，并说明「先解除持久禁用才能重新启用」。理由是它没有可解释的含义——patch 说重启后禁用，内存说现在启用，谁对谁错都是猜。置灰把状态空间收敛成三种。

### 5.6 边界与失败

| 情形 | 行为 |
|---|---|
| 条目来自 bundle 内置 patch | **可用**——home 层覆盖能作用于它（§3.1）。这是相对「只改已有条目」的实质扩展 |
| 条目只在本次运行存在（面板新建） | 明确报错：它还没写进任何 patch 文件，重启后本就消失 |
| 条目 id 来自 `include:` 前缀 | 用裸 id 写入（§5.3） |
| home 层文件不可写 | 报出真实原因（权限），不吞成「条目不存在」 |
| `profileContext` 缺失（非 dsh 启动） | 写入照常（home 层），读取只有 home 层 |

## 六、验证

已完成的（2026-11-15）：

- **真机（隔离 dev 实例，`DSH_HOME=.ssid-iso-test/home-100`）**：对 `mcp-probe` 点「永久禁用」→ home 层 patch 只追加 33 字节、既有内容（含 `- id: webserver` 的端口覆盖与全部注释）逐字不变 → 探针的 MCP 子进程即时退出 → **重启实例后它没有启动**，`listMcpServers` 报 `{disabled: true, permanentDisabled: true, sessionToggled: false}`；同时 `playwright-headless` / `playwright-headed` / `codegraph` 三个带 `disabled: !!js ...` 的条目正确保持 `permanentDisabled: false`（表达式没有被误判成字面量）。解除后文件**逐字节还原**到 564 字节的原始状态，探针进程重新启动。
- **真实 patch 演练**：拿 `~/.dsh/profiles/ssid/cordis.patch.yml`（11,782 字节、含 `!!js` 与注释）走写入/解除，只追加 37 字节，`!!js` 表达式一字未动。
- **`applyEntryPatches` 直接验证**：`insert` 子条目 + 顶层覆盖 → `disabled: true` 且 `config` 保留；去掉覆盖 → 完全还原。
- `typecheck` / `test`（79 条）/ `build`（幂等、工作树干净）三关。

单元层面由 `tests/mcp-permanent-disable.test.ts` 的 19 条测试钉住：字节保真、CRLF、幂等、同 id 取最后一个、行尾注释、`include:` 前缀逐层剥、`!!js` 不计入、bundle 条目可钉、面板新建与不存在 id 报错。

## 七、未决

1. **`createMcpServer` 不落盘**：面板新建的 server 重启即消失，所以对它做「永久禁用」没有意义（§3.5 只能报错）。要不要让增删改也写 patch，是独立的一条，比方案 A 大。
2. **home 层的跨 profile 影响**要不要给用户一个「只在本 profile 生效」的选项？如果给，就得面对 §3.4——对 `owned` 条目那个选项是假承诺，只能在界面上对它们禁用该选项。这需要插件知道模板 `owned` 集合，跨包耦合，暂不做。
3. **`profile-seed` 的触发条件**：§3.4 的退役判据是确定的，但 seed 实际多久跑一次（每次启动 / 仅版本变化）没有查到底。写入 home 层不受影响，这条只影响「如果将来改回 profile 层」的判断。
