# MCP 开关的持久化边界：设计方案（2026-10-25）

> 状态：**设计待评审**（方案 B 待实现）
> 关联：GitHub `Max-Null/dsh-skill-mcp-center#6`、`#7`；`docs/设计/Skill与MCP管理中心-spike记录.md` §1.5

## 一、问题

面板关掉一个 MCP server，重启 DSH 后它又回来了，工具重新注入会话（#6 实测：一个 `rea` server 207 个工具）。

根因不在插件，在宿主：

- `ctx.loader.update(id, { disabled })` 在**内存树**上生效——`Entry.update` 会 `_dispose` 掉 fiber，连接断开、工具卸载，当次运行立即见效。
- 但 `EntryTree.update` 结尾调用的 `source.tree.write()` 落到 `Loader.write()`，而它是空函数：`@deepseek-ai/cordis-plugin-loader@1.0.2` 的 `lib/index.js:715` 是 `write() {}`，DSH 源码 `vendor/loader/src/index.ts:171-173` 的注释写明「Loader's root tree is in-memory; writes are no-ops」。
- 重启后从 `cordis.yml` / `cordis.patch.yml` 重新加载，`disabled` 不存在 → 恢复启用。

一句话：**开关的效力只到本次运行，但界面按「持久设置」的语义呈现它。**

## 二、目标与非目标

**目标**：让开关的效力边界在界面上可读——用户按下开关时就知道「重启后它会回来」，不再把它当作持久设置。

**非目标**：
- 不程序化修改用户的 `cordis.patch.yml`（方案 A，见 §四）。
- 不向上游发 feature request（方案 C，是独立动作，不在本库的交付里）。
- 不改 `mcpStatus()` 的状态推导——`entry.disabled` 本身是对的（读 `options.disabled` 与祖先链），问题只在**语义呈现**。

## 三、方案 B：把边界写进界面

### 3.1 提示位置

两处，各自解决不同的问题：

| 位置 | 文案 | 解决什么 |
|---|---|---|
| MCP 区块标题下 | 「开关只对本次运行生效，重启后恢复。要长期禁用，见说明。」 | 一次讲清楚规则，不重复 |
| 开关处于「关」的条目行 | 「本次运行已停用 · 重启恢复」 | 关掉的当下看得见后果 |

只在**关**的状态显示行内提示：开着的条目显示提示是噪音（28 个 server 每行带一句，读到第三行就失效了）。

### 3.2 状态一致性

`listMcpServers()` 的 `disabled` 来自 `entry.disabled`（getter，含祖先禁用）。手写 patch 加 `disabled: true` 的条目，加载后该 getter 应为真，面板显示「关」——与 #6 作者「面板可能仍显示启用」的观察冲突，需要实测确认；若实测确实不一致，是读取路径的缺陷，另开一条。

### 3.3 文案与 i18n

新增字典键（zh / en）：

- `mcpSessionOnlyTitle`：`MCP 开关只对本次运行生效 · 重启后恢复` / `MCP switches apply to this run only · reverted on restart`
- `mcpSessionOnlyOff`：`本次运行已停用 · 重启恢复` / `Disabled for this run · restored on restart`

`verify-client-ui-i18n` 会检查硬编码文案，两语都要进字典。

### 3.4 为什么不是「禁用时写一个自定义字段」

插件可以自己在存储里记一份「用户想禁用的清单」，面板显示时与 loader 状态取交集——但那只是**展示层假装持久**：重启后 server 仍会被加载、工具仍会注入，除非插件能阻止 MCP client 启动。它不改变事实，只是让事实更难被发现。不做。

## 四、为什么不选 A（程序化写 patch）

把 #6 作者的 workaround 自动化（给 `cordis.patch.yml` 的对应条目插 `disabled: true`）在技术上可行，但要先解决四件事：

1. **条目 id 稳定**：`mcp-<serverName>` 是面板新建时的约定，手写 patch 的条目可能不遵守。
2. **patch 文件定位**：`$DSH_HOME/profiles/<p>/cordis.patch.yml`，多 profile、隔离实例（`SSID_PROFILE_NAME`）各有各的。
3. **模板覆盖**：`profile-seed` 按子条目 id 合并，「出厂条目以模板为准」——用户自建的 MCP 条目不在模板里，风险较小，但需要机械判据确认哪些条目是「用户的」。
4. **写文件 = 改用户的配置文本**：注释、格式、`!!js` 表达式都会被重写，`yaml` 序列化不保序不保注释。

这四件事都成立之前，程序化写 patch 会制造「看起来成功、实际被下次 seed 覆盖」的假象——比诚实标注更糟。

## 五、验证

- `typecheck` / `test` / `build` 三关。
- 组件测试：开关为「关」时渲染行内提示；为「开」时不渲染；标题下的说明始终渲染。
- 真机（dev 实例）：关掉一个 server → 提示出现；重启 → server 回来、提示消失（与 #6 的行为一致）。

## 六、未决

1. 行内提示是否也要在**手写 patch 禁用**的条目上显示？那种条目的「关」是持久的，显示「重启恢复」会误导。判据：只对**本次运行内被面板改过**的条目显示——这需要插件记住「本次运行改过哪些」，成本不高（一个 Set）。
2. 标题说明里的「见说明」指向哪——面板内没有长期禁用的操作入口，可能改成「要长期禁用，在 `cordis.patch.yml` 给条目加 `disabled: true`（见 README）」。
